## V2 rewrite (branch `v2` / `fm/*`)

* Toolchain: `global.json` pins SDK 11 preview with `rollForward: latestFeature`. Multi-TFM is `net8.0;net9.0;net10.0;net11.0` in `Directory.Build.props`. `AnalysisLevel` is pinned (`9-all`), not `latest-all`, because TreatWarningsAsErrors + unpinned latest breaks on new SDK waves.
* Package layout: `Client` (receive/dispatch/webhook), `Handlers` (attrs/contexts/routing; embeds Generators under `analyzers/dotnet/cs` in the nupkg), `Generators` (netstandard2.0 Roslyn, not published alone), `Hosting` (BackgroundService + SetMyCommands; **no** ASP.NET Core framework reference - polling-only console/worker bots must stay runnable on the base runtime image), `AspNetCore` (the sole `FrameworkReference Microsoft.AspNetCore.App`; owns `MapTelegramWebhook`), metapackage `Vexel.Telegram` (`IsPackable=false` until publish decision; deliberately excludes `AspNetCore`).
* Client dispatch: `VexelClient` receives via polling (default) or webhook (`TelegramReceiveMode`; XOR validated by `VexelClientOptions.ValidateReceiveMode` at start). Polling deletes any leftover webhook then long-polls; webhook mode calls `setWebhook` with `secret_token` and waits (a `Webhook.Url` path that differs from `Webhook.Path` only warns - proxies legitimately rewrite) - ingress is `WebhookUpdateReceiver` behind an **explicit** `MapTelegramWebhook` call (`Vexel.Telegram.AspNetCore`; nothing auto-mapped; endpoint is `AllowAnonymous` because `secret_token` is the auth and an app-wide fallback policy would 401 Telegram first; bad/missing secret → 403). `UpdateScheduler` runs ordered-per-chat lanes (bounded await-backpressure, idle eviction); `UpdateDispatcher` (concrete, no `IUpdateDispatcher`) is the routed → On* → raw seam - exactly one `IUpdateRouter` (`TelegramRouter` runs routed then On* fan-out; a foreign `IUpdateRouter` registration fails fast) and raw handlers only from `AddRawUpdateHandler<T>`; handler faults are isolated per update/handler and never kill the lane or receive loop. Fatal receive errors rethrow from `VexelService` so the host stops (no zombie), but a stop that lands mid-`setWebhook`/`deleteWebhook` is normal shutdown, not fatal - Telegram.Bot wraps the cancellation in `RequestException`, so it has to be unwrapped (`IsShutdownCancellation`).
* SetMyCommands: auto at host start from `IBotCommandCatalog` (`TelegramRouter`) via `SetMyCommandsInitializer`; opt out with `VexelClientOptions.RegisterBotCommands = false`. Empty descriptions fall back to the command name. Command metadata is cosmetic, so it never fails host start: an empty payload is skipped (sending `[]` would wipe the BotFather menu) and Telegram-side faults are logged and swallowed. Fail-fast stays for real config errors (receive-mode XOR) and the receive loop.
* Lane keys: message chat id; callback `Message?.Chat.Id ?? From.Id`; inline/chosen `From.Id`; otherwise global (`UpdateLaneKey`).
* Per-update DI: one `AsyncServiceScope` per update; `IUpdateScopeInitializer` runs before handler resolve so Handlers can bind write-once `UpdateContextHolder`. Contexts + concrete `Feedback` are scoped factories over the holder (wired by `AddTelegramBot`; the per-piece helpers are `internal`).
* Contexts: `MessageContext`, `CallbackContext` (nullable `ChatId`), `InlineQueryContext`, `ChosenInlineResultContext`. `Feedback` is thin (Reply/Edit/AnswerCallback/AnswerInline/SendWithKeyboard); answer methods are first-wins idempotent and only latch after the Bot API send succeeds. `Edit` needs a bot-authored message (callback or chosen inline result); plain message updates throw.
* App DI entry: `AddTelegramBot(...)` (client + host + contexts + Feedback + Flow/`IFlowStore` + `TelegramRouter`). Compose with Immediate `AddXxxHandlers()` + generated `AddXxxTelegram()`.
* Routing (T3/T5/T6/T7/T8/T9): dual-attr Option A - `[Handler]` + `[Command("name")]` / `[Callback("key")]` / `[InlineQuery("trigger"|"")]` / `[ChosenInlineResult("key")]` / `[OnMessage|OnCallbackQuery|OnInlineQuery|OnChosenInlineResult]`. Generator seeds FAWMN on `HandlerAttribute`; command/callback/inline/chosen maps keep route-attr types; **flow step map** is pure text steps only - `[Handler]` with empty/single-string request and *no* route/On* attr; **On*** observers take empty request only (inject context for payload). Emits `Add{Assembly}Telegram()` registering a `TelegramRouteContribution` (frozen route maps + On* arrays sorted by handler FQ metadata name + binders that `GetRequiredService<X.Handler>()` + `[Command]` metadata for SetMyCommands). `TelegramRouter` implements `IUpdateRouter` + `IBotCommandCatalog` and runs routed then On* (always, sequential, FQ-name order, fault-isolated per observer) before raw handlers in `UpdateDispatcher`. Fire-and-forget On* is post-2.0.
* Binding convention (normative in internal key extractors / `CommandArgumentBinder`): command key from offset-0 `BotCommand` entity; `@Bot` suffix stripped/matched; args bind by request ctor (empty / single string / tokenized primitives; trailing string takes rest). Callback key = `CallbackQuery.Data` up to first `|`; suffix after binds as single string (or empty record ignores it). Inline query routes on query text only (never `InlineQuery.Id`): first whitespace token exact-matches a non-empty trigger, remainder trimmed binds as string; empty/unmatched → empty-trigger default with full query text. Chosen inline result uses ResultId `key|suffix` like callbacks. Flow step payload = `Message.Text ?? Caption ?? ""` (empty or single string). On* requests are empty records only. Keyboard helpers: `Keyboards.InlineKeyboardBuilder` / `CallbackData.Format` emit short `key` / `key|suffix` and enforce the 64-byte UTF-8 cap.
* Flow (T6): concrete `Flow` + `IFlowStore`/`MemoryFlowStore` (namespace `Vexel.Telegram.Handlers`, files under `Flow/`). `PromptAsync<TRequest>` takes the **request** type, not the handler class (`flow.PromptAsync<CollectName.Command>()`) - handler types are static and C# rejects static types as type arguments; step key = `typeof(TRequest).FullName` (nested requests render as `Ns.Handler+Command`), so two handlers sharing one request type is a duplicate route key (the duplicate-key analyzer tracks a `flow step` kind alongside command/callback). The prompt-target analyzer only judges requests declared in the current compilation: metadata is imported with `MetadataImportOptions.Public`, so a referenced library's private `HandleAsync` is invisible and cross-assembly requests are accepted and left to the runtime step-map check. Text precedence: leading-`/` commands win (built-in `/cancel` only if the app has flow steps, has no user `[Command("cancel")]`, and something is actually armed), then armed step, else unrouted; any offset-0 `BotCommand` entity is a command miss and is never step input, including `/foo@OtherBot`. B3 lifecycle: success without re-arm auto-completes; exception keeps armed + generic Feedback reply; TTL default 15m (lazy expiry on read + opportunistic sweep on write); draft is JSON POCO only. Do not put a type named `Flow` inside namespace `*.Flow` (CA1724).
* B4 answer obligation: `IUpdateCompletionHook` runs after the router + raw handlers; `AnswerObligation` discharges default empty `answerCallbackQuery` / empty `answerInlineQuery` (`cache_time: 0`) via scoped `Feedback` when nothing answered (matched throw, unrouted, or silent success). `Feedback.AnswerCallbackAsync` / `AnswerInlineAsync` are first-wins idempotent so app answers win. Analyzer rule IDs live in `src/Vexel.Telegram.Generators/AnalyzerReleases.*.md` - do not restate them here.
* Generator tests: `tests/.../Generators/` runs both Immediate + Vexel generators in-process (composition spike). Handlers types must be `partial`. Do not `InternalsVisibleTo` the Generators assembly from tests - PolySharp `ModuleInitializerAttribute` collides with `System.Runtime`.
* Tests live in `tests/Vexel.Telegram.Tests` (xunit): unit + generator snapshots + `EndToEnd/` host-level polling against an in-process fake Bot API; run with `dotnet test`.
* Handlers references `Immediate.Handlers` as a normal PackageReference (no PrivateAssets) so consumers get it transitively. Generators is an Analyzer ProjectReference with `PrivateAssets=all` for monorepo builds, and is packed into the Handlers nupkg under `analyzers/dotnet/cs` (`_PackEmbeddedGenerators` in the Handlers csproj).
* Packaging: `bash ./build/pack.sh nupkgs` then `bash ./build/assert-pack-layout.sh nupkgs` (both used by `build.yml` / `release.yml`); the packable project list lives once in `build/packable-projects.sh`. Embedded generator is built against Roslyn 4.14, so **package consumers need SDK 10+** (documented in README + `docs/v1-to-v2.md`) even though libs still target net8.0. CI `test` job matrices `net10.0`/`net11.0` and runs parallel to `build` (no `needs:`); release publishes only on a `v*.*.*` tag ref - `workflow_dispatch` is a pack dry-run.
* Sample bot: `samples/Vexel.Telegram.Sample` is the v2 living docs (in the solution build). Three-call wiring in `Program.cs`; token via `TELEGRAM_BOT_TOKEN` / user-secrets `BotToken` (see sample README). Monorepo consumers must ProjectReference `Vexel.Telegram.Generators` as `OutputItemType=Analyzer` themselves - analyzer ProjectReferences do not flow transitively; NuGet consumers of Handlers get the generator from the nupkg.
* Central package versions live in `Directory.Packages.props`. Microsoft.Extensions is on 10.0.x to satisfy Immediate.Handlers TFM floors.
* `docs/v2-context.md` owns the v2 design decisions and decision log; check it before proposing API or architecture changes.
